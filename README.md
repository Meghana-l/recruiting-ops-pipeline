# Recruiting Pipeline

**[See it live →](https://recruiting-ops-pipeline.vercel.app/)**

A small project about a problem most companies have and nobody enjoys: recruiting data
is a mess, and nobody can answer simple questions about hiring without rebuilding a
spreadsheet by hand.

This takes a messy export of job applications, cleans it up, and turns it into a
dashboard you can actually use.

---

## The problem

Imagine you run hiring at a company. Someone asks you three questions:

- How long are we taking to hire engineers?
- Which candidates have we gone quiet on?
- Is LinkedIn actually worth what we pay for it?

These sound easy. They aren't, because the answers live in two different systems that
don't talk to each other. Applications sit in one. Job openings sit in another. They're
supposed to be linked by a job ID, and sometimes that ID doesn't match.

On top of that, the data is full of small human problems. Someone typed "linkedin",
someone else typed "LinkedIn", a third person typed "LINKEDIN". A candidate applied
twice and now counts as two people. A job was deleted while people were still applying
to it.

Any one of those is minor. Together they mean you can't trust a single number, and
answering a basic question takes a person half a day.

## What this does

It takes the messy export, fixes it step by step, and publishes a dashboard.

**444 applications go in. 405 come out that you can trust.**

Here's what happened to the other 39:

| What was wrong | How many | Why it matters |
|---|---|---|
| Applied on a date in the future | 6 | A time zone bug upstream. Breaks any report by month. |
| Activity recorded before they applied | 12 | Old records where the timeline runs backwards. |
| Applied to the same job twice | 12 | Counting them twice makes the funnel look better than it is. |
| Job no longer exists | 9 | The role was deleted after people applied to it. |

That last one matters more than it looks. Those 9 are real people who applied for a
real job. Deleting them would be the easy thing to do. Instead they get written to a
separate file so a recruiter can go and reassign them. Nobody disappears quietly.

## What you can see on the dashboard

The live site has two parts.

**Overview** — the numbers a hiring team would care about. How many people are in the
pipeline, where candidates drop out, which sourcing channels actually produce hires
rather than just applications, how long each team takes, and a list of candidates
nobody has followed up on. You can filter all of it by team, region, or source and
everything recalculates.

**Data** — the actual rows. You can switch between the cleaned data and the original
messy export. In the raw view, every problem is highlighted in red in the exact place
it occurs, so you can see the mess for yourself rather than taking my word for it.

## A thing I decided not to do

The checks at the bottom of the dashboard don't all pass. Two of them fail, on purpose.

Ten applications have no email address. A program can't invent an email, and guessing
one would be worse than leaving it blank. The real fix is making the field required on
the application form, which is a conversation with the recruiting team, not a line of
code. So it gets flagged for a human instead of quietly patched over.

One job offer sits outside the approved salary range for that role. That might be a
mistake, or it might be an exception somebody already approved. A program shouldn't
decide which. It gets flagged for Finance to look at.

I think this is the more honest version. A dashboard where everything is green usually
means somebody hid something.

## How it's built

Python creates the fake data and runs the pipeline. The cleaning rules are written in
SQL. There are 18 tests that check each rule does what it claims. The dashboard is a
single page that reads one file.

```
sql/      the cleaning rules
src/      generates the data, runs the pipeline, builds the dashboard
tests/    18 tests covering the rules
public/   the dashboard
```

To run it yourself:

```bash
pip install -r requirements.txt
./run.sh
```

Then open `public/index.html`.

## About the data

All of it is made up. There is no real candidate information anywhere in this project.
The data is generated by `src/generate_data.py`, with the messiness added deliberately,
because clean practice data wouldn't prove anything.
